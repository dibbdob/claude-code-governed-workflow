# Ticketdesk

The rules a support desk uses to set a ticket's priority and its response deadline. Plain JavaScript (ES
modules), no dependencies, Node's built-in test runner.

A rule in this file is a pointer at whatever enforces it. When a lesson can be checked, the check goes in
`build.sh` and only the pointer stays here ([ADR 0001](docs/adr/0001-a-rule-points-at-what-enforces-it.md)).

## Build

```bash
./build.sh
```

The whole of it is the gate; a test file you chose to run is not.

## Specs: OpenSpec

What to build is in OpenSpec ([ADR 0008](docs/adr/0008-specs-are-openspec-changes.md)): `openspec/specs/` is
how the system works now, and `openspec/changes/` holds approved changes still to deliver. Propose one with
OpenSpec's `openspec-propose` skill (`/openspec-propose`), named after its GitHub issue (`57-bank-holidays`).
A change is ready once its pull request is merged. OpenSpec's skills, in `.agents/skills/` and linked from
`.claude/skills/openspec-*`, are generated by `openspec init` and refreshed by `openspec update`; do not edit
them.

A test names the scenario it covers in its title, `[response-deadline] A ticket opened late on a Friday`, and
`build.sh` fails when a scenario in `openspec/specs/` has no test naming it, and when an archived change has
tasks left undone. A change may be revised while it is delivered, as OpenSpec intends, while its intent holds;
archiving lists every revision for a person to confirm. `openspec/config.yaml` holds the rules for that and
for risk: every proposal states a risk level, and a medium or high one gets a design with mitigations.

`build.sh` runs one at a time per checkout (`.build.lock`).

## Delivering a change

`/deliver <change>` takes an approved change from its own folder to a pull request description, archiving
the change on the way ([command](.claude/commands/deliver.md)). It uses OpenSpec's `openspec-apply-change`
skill for the building, with this project's build rules in `openspec/config.yaml`, and adds the gates, the
reviewer and the archive around it. It reads through the `spec-reader` subagent first
([ADR 0002](docs/adr/0002-reading-is-delegated-to-a-subagent.md)), and is reviewed by the
`independent-reviewer` subagent, pinned to one commit and given no rationale
([ADR 0003](docs/adr/0003-the-reviewer-is-not-told-why.md)). The spec-reader has no shell
([ADR 0006](docs/adr/0006-an-agent-that-can-do-without-a-shell-gets-none.md)); the reviewer's Bash is held
to read-only commands by a hook in its frontmatter, whose tests run in `build.sh`
([ADR 0004](docs/adr/0004-a-restriction-is-a-hook-not-a-sentence.md)). After changing the hook, run
`./build.sh`; nothing else exercises it outside a session.

`.claude/settings.json` allows the build and read-only git, and denies `git push` and `git reset --hard`.

Each delivery has a folder of its own, made by `scripts/start-delivery.sh <issue-or-change>`; a change's
GitHub issue says who is delivering it, `scripts/claim-delivery.sh` is the only thing that assigns it, and
`scripts/finish-delivery.sh` opens the pull request
([ADR 0007](docs/adr/0007-a-team-delivers-the-way-git-works.md)). Their tests run in `build.sh`.

`./scripts/agent.sh <issue-or-change>` runs the same delivery headless, in its own folder, and finishes it.

## The plugin

`plugin/` is a marketplace holding one plugin, `governed-delivery`, generated from `.claude/` by
`python3 tools/package_plugin.py`. Edit `.claude/`, regenerate, and commit both; `build.sh` fails when they
differ ([ADR 0005](docs/adr/0005-the-plugin-is-generated-from-the-project.md)).
