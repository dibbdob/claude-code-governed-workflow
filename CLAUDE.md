# Ticketdesk

The rules a support desk uses to set a ticket's priority and its response deadline. Plain JavaScript (ES
modules), no dependencies, Node's built-in test runner.

A rule in this file is a pointer at whatever enforces it. When a lesson can be checked, the check goes in
`build.sh` and only the pointer stays here ([ADR 0001](docs/adr/0001-a-rule-points-at-what-enforces-it.md)).

## Build

```bash
./build.sh
```

The whole of it is the gate; a test file you chose to run is not.

## Specs: OpenSpec

What to build is in OpenSpec ([ADR 0006](docs/adr/0006-specs-are-openspec-changes.md)): `openspec/specs/` is
how the system works now, and `openspec/changes/` holds approved changes still to deliver. `/refine` writes
one from a GitHub issue and names it after the issue (`57-bank-holidays`).
A change is ready once its pull request is merged. OpenSpec's skills, in `.agents/skills/` and linked from
`.claude/skills/openspec-*`, are generated by `openspec init` and refreshed by `openspec update`; do not edit
them.

A test names the scenario it covers in its title, `[response-deadline] A ticket opened late on a Friday`
(where tests are and how a title is read: `scripts/test-citations.json`,
[ADR 0012](docs/adr/0012-where-the-tests-are-is-the-projects-to-say.md)), and
`build.sh` fails when a scenario in `openspec/specs/` has no test naming it, when a scenario in an open change
is not a Gherkin outline whose placeholders match its table of worked examples
([ADR 0007](docs/adr/0007-a-scenario-is-an-outline-with-worked-examples.md)), and when an archived change has
tasks left undone, or when an open change's tasks do not end with the Delivery group: grounding, the review,
the second review and verify, which `/deliver` ticks as it does them
([ADR 0009](docs/adr/0009-a-deliverys-steps-are-tasks.md), [ADR 0011](docs/adr/0011-grounding-is-a-delivery-task.md)).

A change may be revised while it is delivered, as OpenSpec intends, while its intent holds; archiving lists
every revision for a person to confirm. `openspec/config.yaml` holds the rules for that and
for risk: every proposal states a risk level, and a medium or high one gets a design with mitigations.

The rules are also kept as worked examples in `test/fixtures/desk-rules.json`, worked out by hand and checked
by `build.sh` ([ADR 0007](docs/adr/0007-a-scenario-is-an-outline-with-worked-examples.md)). A change to a rule
changes that file too.

`build.sh` runs one at a time per checkout (`.build.lock`).

## Refining a change

`/refine <issue>` turns an issue into a change with the person who raised it, up to a spec pull request
([command](.claude/commands/refine.md), [ADR 0010](docs/adr/0010-refinement-is-a-command-too.md)). It writes
only the change folder. In a session, `scripts/refinement.sh` is the one way it reaches GitHub: `git push`
stays denied. On GitHub, the `refine` label drafts it and `@claude` comments on the spec pull request revise
it ([`refine.yml`](.github/workflows/refine.yml)). When the change is merged, `refined` labels the issue
`ready` and writes the change's summary on it with `tools/issue-summary.mjs`.

## Delivering a change

`/deliver <change>` takes an approved change from its own branch to a pull request description, archiving
the change on the way ([command](.claude/commands/deliver.md)). It uses OpenSpec's `openspec-apply-change`
skill for the building, with this project's build rules in `openspec/config.yaml`, and adds the gates, the
reviewer and the archive around it. It reads through the `spec-reader` subagent first
([ADR 0002](docs/adr/0002-reading-is-delegated-to-a-subagent.md)), and is reviewed by the
`independent-reviewer` subagent, pinned to one commit and given no rationale
([ADR 0003](docs/adr/0003-the-reviewer-is-not-told-why.md)). The spec-reader has no shell, and the reviewer's Bash
is held to read-only commands by a hook in its frontmatter, whose tests run in `build.sh`
([ADR 0004](docs/adr/0004-a-restriction-is-a-tool-list-or-a-hook.md)). After changing the hook, run
`./build.sh`; nothing else exercises it outside a session.

`.claude/settings.json` allows the build and read-only git, and denies `git push`, `git reset --hard` and the
commands that throw away uncommitted work (`git checkout --`, `git restore`, `git clean`, `git stash drop`).

A delivery runs on a branch of its own ([ADR 0008](docs/adr/0008-deliveries-run-on-the-standard-action.md)).
`./scripts/agent.sh <issue-or-change>` makes one from main in a worktree of its own, beside the checkout, and
runs `/deliver` headless there, then checks it is committed, archived and builds
([ADR 0013](docs/adr/0013-a-local-delivery-has-a-worktree-of-its-own.md)). On GitHub, the `deliver` label runs it through Anthropic's Claude Code
action, set up the standard way ([`deliver.yml`](.github/workflows/deliver.yml)). Both read the tools they
allow from `scripts/headless-tools.txt` and the model from `scripts/delivery-model.txt`, so a change to either
is one edit. Only `agent.sh` takes `--model <model>`, for one run on a model other than the default.

## The plugin

`plugin/` is a marketplace holding one plugin, `governed-delivery`, generated from `.claude/` by
`python3 tools/package_plugin.py`. Edit `.claude/`, regenerate, and commit both; `build.sh` fails when they
differ ([ADR 0005](docs/adr/0005-the-plugin-is-generated-from-the-project.md)).
